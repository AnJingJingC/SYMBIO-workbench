# 零件装配（Part）

> **默认状态：未启用（C 层）。** 技能在位、可手动调用，但不自动跑——它会把外部零件装进本机。
> 装任何联网零件前必须先过 `docs/PRIVACY.md` 的零件评估；面板上的虚线圈属有意为之，不是缺件。

**"一切皆零件"的真正含义是：只拿你要的那一小块，而不是装一整个面板。**

装多了不用反而烧 token——这是作者的判断，也是我们建本机零件库的理由。

## 零件库在哪（真实路径，别凭记忆）

```
parts/
├── 索引.md          # 工具自动重建，手改会被覆盖
├── 机制/<名>/PART.md          纯方法论，无实体文件（或 canonical 指向仓内正本）
├── 技能/<名>/PART.md          实体在 memory/10-shared/skills/<名>/SKILL.md
├── 脚本/<名>/PART.md          实体在 tools/<x>.mjs
├── 技能|脚本/<名>/payload/    仅当实体来自**仓外**才复制一份
└── 待评估/<名>/PART.md        想装但没验证的
```

**本库默认不存副本**：卡片里的 `canonical` 字段指正本路径，`pull` 直接从正本拷。
只有实体来自仓外（比如从别人仓库扒来的脚本）才复制进 `payload/`。
理由：副本一定漂移——本项目的阶段报告和 SKILL.md 都吃过这个亏，改一处漏另一处。

**操作一律走工具，不要手编卡片**（字段名写错就检索不到）：

```bash
node tools/parts.mjs list [--kind 脚本]      # 看全部
node tools/parts.mjs search <关键词>          # 离线检索（名称/标签/简介/正文）
node tools/parts.mjs show <名>                # 看卡片全文
node tools/parts.mjs add --name <名> --kind 脚本 --source "<来源>" --license MIT \
     --desc "一句话" --tags a,b --risk 低 \
     --abilities "能力1|能力2|能力3" --why "不装它的代价" --limits "做不到什么" \
     [--file <源文件>] [--verified]
node tools/parts.mjs pull --name <名> [--to <目录>] [--force]   # 装配实体文件
```

**`--abilities / --why / --limits` 不是可选装饰**：缺了它们卡片会被标成「⚠卡片未补全」。
收录不等于有用——检索到了却读到一堆「（列 2–4 条具体能力）」的占位符，比没收录更浪费时间。

## 三种来源（按可信度排序）

| 来源 | 做法 | 风险 |
|---|---|---|
| **拆自己的**（最高） | 某个流程走顺了 → 固化成技能/脚本 | 低 |
| **拆成熟产品的机制**（中） | 看它怎么解决同一个问题，**只抄思路，不搬代码** | 中（需自己验证） |
| **装公开插件**（最低） | 只在确有必要时，且必须读完源码 | 高（权限等同你本人） |

**默认禁止**：来源不明、未签名、需要联网的外部插件。理由：与 L1/L2 红线冲突。

## 步骤

1. **先问清"要解决什么问题"**，而不是"要装什么"。宿主说"我想自动记账"，不要立刻找记账插件，先确认：记什么账、从哪来、给谁看。
2. **先查库**：`node tools/parts.mjs search <关键词>`。有现成的就 `show` 看边界，别重复造。
3. **没有就拆**：
   - 找到能做这件事的成熟产品/机制（读它的文档与类型定义，**不读源码就不许抄**）
   - 只提取"解决这一个问题所需的最小机制"
   - `parts.mjs add` 收录，写明：能干什么 / 为什么值得装 / 装配方式 / 风险与边界
   - **未验证就先放 `--kind 待评估`**（不传 `--verified`）
4. **验证后翻转状态**：真跑通过了才加 `--verified`。`verified:false` 的零件 `pull` 会被拒绝——这是故意的。
5. **小步试装**：先接到一个场景里跑一次，**不要全工作台铺开**。
6. **体检**：`node tools/memory-lint.mjs`。有不通过就回滚。
7. **回填验证记录**：在该零件的 `PART.md`「验证记录」里写日期 + 怎么验的 + 结果。

## 回滚（装之前就要想好）

- 装之前：把将被修改的文件复制到 `memory/90-archive/pre-part-<零件名>-<日期>/`
- 装之后跑不通：把备份复制回去，在 `PART.md` 里标记"已回滚 + 原因"
- **没有回滚路径的零件，不许装**

## 硬约束

1. **一次只装一个零件**。三个一起装，坏了不知道是谁的错。
2. **零件必须能被单独关掉**（配置开关或独立目录），不能和主流程焊死。
3. **不许装"全家桶"**：需要 5 个功能只装 1 个，其余记进「待评估」。
4. **`verified:true` 必须真的跑过**。把没验证的东西标成已验证，比不收录更糟——下一个人会信它。
5. 涉及联网/读全盘的零件 → 必须过 `/symbio-pii-guard` 评估，并在卡片里把 `risk` 标高。

## 与共享技能的区别（别混）

| | 零件库 `parts/` | 共享技能 `memory/10-shared/skills/` |
|---|---|---|
| 装的是 | 一块**能力**（脚本/机制/技能片段） | 一条**已验证的做事方法** |
| 谁维护 | 人+AI 都能收，靠检索取用 | 场景跑通后 `promote` 提升，`pull` 装配 |
| 生效方式 | `pull` 复制到目标位置 | `pull` 进 `.dsh/skills`（DSH 才加载） |
| 工具 | `tools/parts.mjs` | `tools/shared-skill.mjs` |

## 预期效果

每月 2–3 个零件，三个月后工作台会明显"会干更多活"，而目录不会变乱。
