## 0 · 先纠正我之前一个错误结论（重要）

我在 `GUI边界评估.md` 里写过："**工作台形态 = 1 块业务面板 + 一组 HTTP 路由，这是硬边界**"。
**后半句对，前半句错。**

准确的说法是：**`dsh-desktop-workbenches` 这个封装只开放一个注册槽，但底层 UI 布局系统的全部座位都在场、且未被禁用。**

实测证据（DSH Desktop 0.2.0-rc.2 安装包内 `app.asar` + 全局 `@deepseek-ai/dsh` 包）：

- Desktop 内置了**开源** `@deepseek-ai/dsh-client-ui-layout`（62 个 `dsh-client-ui-*` 插件包全在）；
- 内置 `@deepseek-ai/dsh-client-ui-dockkit`（停靠/浮动面板工具包）；
- `dsh-desktop.patch.yml` 只禁用了 `ui-brand-official`、`ui-settings-account` 两个**品牌/账号**座位，**没有禁用 layout**；
- `@deepseek-ai/dsh` 本体是 **MIT 许可、仓库 `github.com/deepseek-ai/deepseek-harness`**，287 个 Cordis 插件包。

### 现宿主真实拥有的座位（来自 `dsh-client-ui-layout` 的 SlotMap 类型声明）

> **2026-11-05 二次修订**：下表是逐条读 `.d.ts` 后的**更正版**。上一版把 `rightbar` 当成"可追加的右列"是误读——
> 它的注释写的是 **OCCUPIED by the right Sidebar**，注册会**替换宿主右栏**（不报错，只是界面变怪）。
> 真正能追加的只有三处：`sidebar.panellist`、`main`（加新 key）、`shell.overlay`。

| 座位 | 类型 | 当前占位 | 能否追加 | 语义 / 对应作者的哪一项 |
|---|---|---|---|---|

| **`main`** | **keyed** | `conversation` 占一个 key | **✅ 加新 key** | 中央面板按 sidebar entry id 切换 → **多场景切换** |
| **`shell.overlay`** | **list** | 空/可加 | **✅ 追加** | 官方原话"a badge / toast / status pill 都该放这里……这是给你自己的全帧表面的追加座位"，且**点击穿透** → 常驻状态栏 / 亮灯 |
| `sidebar.footer.action` | list | 设置旁 | ✅ 可加 | 侧栏底部动作 |
| `sidebar.brand.mark` / `.name` | single | 品牌位 | ⚠️ 可替换品牌 | 只换 mark/name，不动周边控件 |

| `shell.leading` | single | ui-sidebar 开合控件 | ❌ 已占 | 仅在侧栏完全折叠时挂载（macOS 红绿灯同区） |
| `root` | single | ui-layout 的 AppFrame | ❌ **明令禁止** | "会 shadow 整个 frame，你只剩自己的组件" |
| `sidebar.workspaces` / `sidebar.settings` | single | ui-workspace / ui-settings | ❌ 已占 | — |
| dockkit | Desktop 内置 | — | 待查 | 停靠 tab + 浮动面板（`.d.ts` 不在开源 npm 包内，需真机试） |

另有 `dsh-client-ui-workflow-run`（工作流运行 UI）、`dsh-experimental-client-ui-agent-team`（多 agent 团队）等现成插件在场。

**结论：多面板同屏、常驻状态栏这两项，我之前判成"宿主钉死"，其实是接入点选错。不需要自研壳。**

2. **C 的 `mainProbe:false` 不是「抽查时点没切页」这么简单。** DOM 侧证每次心跳（2s）

3. **"多场景同屏"这个说法要收窄。** `main` 给的是按 key **切换**中央面板，不是同屏并列；
   真同屏仍要 dockkit 浮动面板或 `rightbar`（后者会替换宿主右栏，不可用）。

   证据，本轮**未做跨页点测**，不能算已实测。

## 1 · 方法论层能否到 99.999%？

先说结论：**"99.999% 相似"不是一个可执行的目标，建议换成一个可打勾的口径。**

因为"相似度"混了三个不同的维度，混在一起谈永远说不清：

| 维度 | 定义 | 上限 | 现在 |
|---|---|---|---|
| **A 机制齐备度** | 作者的 29 项机制（逐条列名可对账），我们有几项 | **100% 可达成**（就 29 项，能枚举完） | **24 全 + 2 部分 + 3 形态受限**（A 层 7 项已于 2026-11-05 补齐） |
| **B 行为等价度** | 每项机制真跑过一次、有证据 | **约 95%**，剩下的不可控：网页 AI 改版、宿主版本升级 | 约 70% |
| **C 观感相似度** | 看起来像不像作者的屏幕 | 现宿主 30–40%；自研壳可达 85%+ | 约 30% |

99.999% 只在 A 维度有意义（而且是 100%，不是 99.999%）。B 永远到不了 100%——因为外部网页 AI 随时改版（我们这轮就被豆包占位语、千问迁移域名、智谱思考块坑了三次）。C 属于形态层，与"方法论"无关。

**所以建议的目标是：A 维度里能做的都做齐，B 维度每项附一条验收证据。这比"99.999%"严格得多，也可交付。**
（2026-11-05 实际结果：A 层 7 项已补齐 → 24 全 + 2 部分 + 3 形态受限。剩下 2 部分中 1 项卡在宿主钩子、1 项卡在画布 API。）

## 2 · 现有 DSH Desktop 能不能改造？

**能，而且这是当前性价比最高的路。** 分三种改法，从轻到重：

### 改法 A：只用现成座位（推荐先做，成本最低）
在 workbench 插件里**绕过 `desktopWorkbenches` 封装，直接向 SlotRegistry 注册**。

> **2026-11-05 真机更正**：下面这段原本写的是 `ctx.uiRenderer.register(...)`，**那是错的**。
> `uiRenderer` 在业务插件的客户端上下文里不是这么用的。真机跑通的形状如下
> （出自 `seat-probe/client.js`，四条通道全部 `ok:true`）：

```js
// 主插件返回 { inject: ['desktopWorkbenches'], apply }，不要声明 slots。
// 读 ctx.slots 会触发 Cordis Proxy 的 "cannot get property slots without inject"。
// 正确取法：门面提供的免声明查询 ctx.get('slots')。
const slots = ctx.get('slots')
if (!slots) return   // 服务未交付，别硬来

// 每个座位先 inject 等它「被声明」的回调，再在回调里 register。
slots.inject('shell.overlay', () =>
  slots.register({ name: 'shell.overlay', id: 'symbio-status', order: 900 }, StatusPill))     // list：常驻状态条
slots.inject('sidebar.panellist', () =>
  slots.register({ name: 'sidebar.panellist', id: 'symbio-scene-b', order: 900 }, PanelIcon)) // list：侧栏按钮
slots.inject('main', () =>
  slots.register({ name: 'main', key: 'symbio-scene-b' }, ScenePanel))                        // keyed：注意是 key 不是 id
```

- 常驻状态栏 → `shell.overlay`（**list 座位，追加不替换，官方就是为这个场景设计的，还点击穿透**）
- 多场景切换 → `sidebar.panellist`（list，加按钮）**+** `main`（keyed，加 key）；两者同名可行，是否强制同名未验
- ❌ **不要用 `rightbar`**：它已被宿主右栏占用，注册会替换掉右栏而不是并排
- ❌ **不要用 `root`**：会 shadow 整个 frame
- 不动 Desktop 任何文件，不进 patch.yml，卸载即干净。

**风险已收敛**：`slots` 服务可达、`inject`+`register` 形状正确、`main` 用 `key`，三点均已真机验证。
尚未验证的是：list id 与 main key 是否**必须严格同名**（注释写"addresses the matching main panel"，
读代码读不出来）、以及点选侧栏条目后 keyed 面板的渲染与跨页常驻。这些属接入细节，不改变「座位开放」的结论。

### 改法 B：patch.yml 插入自己的插件
宿主 `dsh-desktop.patch.yml` 支持 `insert` / `disabled` / 改 `config`（官方自己就这么用：禁 brand、插 workbenches）。
可以插一个自己的 UI 插件、或**禁用现有 workbenches 换成多面板实现**。

- 能力比 A 强（能改宿主插件组成）
- 代价：改的是**安装目录下的文件**，宿主升级会被覆盖，需要恢复脚本；也更容易在宿主升级后崩（我们已经被 `h` 遮蔽那类问题坑过一次）

### 改法 C：给 DSH 官方提需求
`deepseek-harness` 是 MIT 开源，`dsh-desktop-workbenches` 的 `register` 签名只给单面板。
可以开 Issue 请求"允许注册多面板 / 暴露 layout 座位"。**但不要等**——A 已经能解决大部分。

**顺序建议：A 先验证 → 够用就停 → 不够才考虑 B → C 只作为长期并行项。**

## 3 · 自研外壳需要什么条件、怎么做？

自研壳的**真实成本比"极高"低**，因为不用从零写 Harness：MIT 开源的 287 个插件包直接复用，自研的只是"壳那一层"。

### 必须满足的条件（缺一不可）

| # | 条件 | 说明 |
|---|---|---|
| 1 | **MIT 合规** | 保留 `LICENSE` 与版权声明；不得暗示官方背书；包名不得占用 `@deepseek-ai/*` |
| 2 | **版本跟随** | Harness 当前是 `0.2.0-rc.2`，rc 阶段 API 会变。必须有升级测试与回滚（我们已有 `symbio-rollback` 的机制可复用） |
| 3 | **插件契约兼容** | 复用 `cordis` + `patch.yml` 组装方式，否则失去全部现成插件 |
| 4 | **生命周期权威** | 进程守护、崩溃恢复、安全模式（Desktop 有 `safe-mode.html` / `plugin-recovery.html`，自研要自己做） |
| 5 | **更新与回滚** | `app-update.yml` 那套；至少要有"拉不起来能退回上一版" |
| 6 | **跨平台** | Win/macOS/Linux 三套窗口chrome、托盘、权限（作者只在 Win 上跑，我们至少要覆盖 Win + mac） |
| 7 | **安全边界** | 网页 AI 桥的登录态存储、凭证分区、L0 宪法的写权限控制 |

### 做法（四步）

1. **组装**：写自己的 `patch.yml`，把 `dsh-client-ui-layout` 换成/扩展成多面板布局（这是自研壳唯一真正的技术增量）。
2. **套 Electron**：主进程负责窗口、托盘、更新；渲染层仍是 Cordis 组装的 React。
3. **复用而不重写**：记忆层、技能层、桥、工具全部零改动（它们本来就是文件 + Node 进程，与壳无关）。
4. **验证链**：每改一步跑一次 `npm run verify` + `smoke` + `test-site`（我们的三层测试可直接用）。

### 什么时候才值得自研壳

只有在**改法 A + B 都做完，仍然缺**下面这些时，才值得：
- 真正的突触画布大屏（可控缩放/拖拽/实时动画，不是 SVG 小图）
- 三场景同屏 + 实时接力演示
- 多显示器各自独立的场景窗口

否则自研壳就是**为了 10% 的观感，付 100% 的维护成本**——而且作者自己也说"不要完全用我的开源，按我的思路建立属于你的智能体"。

## 4 · 推荐路线（按此顺序，每步都有停止条件）

```
第 1 步  方法论收口 7 项（零依赖）        → ✅ 2026-11-05 完成（24 全 + 2 部分 + 3 受限）
第 2 步  座位小样验证                     → ✅ 2026-11-05 真机完成（0.1.3，四行全通）
                                   探针从 0.1.0 到 0.1.3 走了四轮：清单被安装器拒绝 →
                                   上报链路四处缺陷 → Cordis inject 门槛 → 三级取服务路径。
                                   真机结论与判读边界见本文开头「真机验收落定」，
                                   不可变证据在 reports/座位探针-验收定稿.json。
                                   探针使命已完成，按 UNINSTALL-PROMPT.txt 卸载。
第 3 步  负载胶囊 + 双面板 + 亮灯         → **已解锁，可开工**；停止条件：观感够用就停
第 4 步  若不够 → patch.yml 插自己的 UI 插件 → 停止条件：再不够才进第 5 步
第 5 步  自研壳（只在上述全做完仍缺时）      → 成本：数周 + 长期跟版本
```

**核心判断：现宿主的上限比我上次说的高得多。第 2 步已在真机验证通过——三处座位全部开放，
改法 A 不再需要自研壳；要不要自研壳，现在只取决于「同屏 + 大画布 + 多显示器」这些形态需求值不值。**
