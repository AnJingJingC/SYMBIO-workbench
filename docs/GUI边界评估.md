# GUI 边界评估（优先级 D）

> 目的：据实评估「多面板网格 / 2D 拓扑 / 常驻状态栏 / 多场景同屏」四项，区分**宿主契约硬限制**与**单面板内可落地**，给出接受结论与弥补建议。

## 宿主契约事实（决定边界）

`dsh-desktop` 工作台插件只开放两个注册位（已查源码确认）：

1. 服务端：`connection` → 注册 `/api/<id>/*` HTTP 路由。
2. 客户端：`desktopWorkbenches.register({...}, panel)` → **注册一块业务面板**，右侧由宿主原生会话占用。

`DshClientManifest.inject` 官方注释明确：**"Informational package-name dependencies, not Cordis service injection"**——面板注入不是 Cordis 服务注入，宿主 Agent 没有"工作台工具注册"服务，也没有"第二块可停靠面板"的注册位。

结论：**工作台形态 = 1 块业务面板 + 一组 HTTP 路由**。这是硬边界，换不掉的。

## 四项逐项评估

| 项 | 形态诉求 | 契约判定 | 本版落地 |
|---|---|---|---|
| 多面板网格 | 多块可停靠面板并排 | ❌ 宿主不给第二块面板 | **接受边界**。在单面板内用响应式 2 列网格（`.sb-main`）逼近"分区"观感 |
| 2D 拓扑 | 画布/拓扑视图 | ⚠️ 不能独立画布面板 | ✅ **已落地**：面板内嵌「系统拓扑 · 单面板内」SVG 流水线（摄入→卡片→记忆；卡片→桥·试问；卡片→工具箱） |
| 常驻状态栏 | 始终可见的状态条 | ⚠️ 不能宿主级状态栏 | ✅ **已落地**：header 改为 `position:sticky` 吸顶（毛玻璃 + 下边框），滚动时状态灯/版本常驻 |
| 多场景同屏 | 同时看多个场景 | ❌ 宿主只加载一块面板、单一上下文 | **接受边界**。面板内可加场景切换下拉（若 `memory/20-scenes` 下有多个场景且后端按场景出 state），但"同屏多场景并排"做不到 |

## 已落地的两项（单面板内）

- **常驻状态栏**：`.sb-head` 吸顶。数据源灯、桥灯、阶段、版本、刷新按钮在面板滚动时始终可见。
- **2D 拓扑**：`Topology` SVG 组件，320×152 viewBox，自适应宽度。节点为矩形框 + 箭头，直观表达 SYMBIO 流水线；桥的"试问"用虚线回流弧表示反问宿主对话。

## 已接受的边界 + 弥补建议

1. **多面板网格 / 多场景独立面板**：宿主形态限制。若要真正多面板/多场景同屏，需换载体：
   - 用 mydsh.xyz 的现成零件（如独立壳模板、echarts 图表、open-design/archify 设计件）在**独立 Electron 壳**里自绘多面板；
   - 或等 dsh-desktop 开放"多面板 / Agent 工具"契约后再映射。
2. **换载体代价**：当前工作台已深度绑定 dsh 面板契约（React 面板 + HTTP 路由 + 六层记忆扫描），整壳重写成本高。**建议**：保持工作台作为"单面板知识中枢"，把重度可视化需求（多面板/拓扑大屏）放到独立壳或市场零件，二者通过 `/api/symbio/*` 共享数据源。

## 诚实红线

不谎称"已实现多面板/多场景同屏"。本版交付的是**单面板内的状态栏 + 拓扑图**，以及清晰写明的宿主形态限制。任何超出单面板的能力都标为"需换载体"，不计入本工作台承诺。
